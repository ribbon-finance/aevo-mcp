# Lessons
- Funding scheduling snapshots must preserve funded instrument entries even when no accounts hold positions at that epoch; `HasPendingCharge` relies on non-nil epoch+instrument buckets to track pending funding charge windows.
- For mode-specific user UX rules (like one-way opposite-direction `reduce_only`), gate validation by both position mode and order actor/path; never let user-order gating block internal `FORCE`/`LIQUIDATION` execution flow.
- For one-way opposite-direction UX enforcement, scope checks to external entry subjects (`api`/`teller`); applying the same gate to eventstream/internal subjects can break ADL/copytrade/planner test and runtime flows.
- Before handing off multi-file changes, run the same lint command the user runs (`make lint`) and fix all findings proactively.
- In sandboxed environments, set `GOCACHE` and `GOLANGCI_LINT_CACHE` to writable paths (e.g., `/tmp/...`) to avoid false lint/tooling failures from cache permission issues.
- When the user requests tests without `-count`, run them as-is; do not add `-count` for single tests.
- When a user flags a mistake or confusion, re-check units/scale (e.g., fixed-point inputs) and verify assumptions before concluding.
- Use the `apply_patch` tool directly for patch edits; do not invoke it via `shell_command`.
- If the user opts to keep a legacy or risky behavior, revert changes and align/remove tests to match their decision, while documenting the rationale.
- Avoid hard-coded dust thresholds for positions; prefer instrument- or config-driven thresholds (e.g., amount step size) so future markets remain correct.
- When the user requests a specific enforcement layer (e.g., API handler instead of core margin), implement there and adjust tests/behavior accordingly, while noting any bypass risks.
- If the user stashes or rolls back prior changes, re-check repo state and realign the plan/tests before proceeding; don’t assume earlier fixes still apply.
- When tightening risk rules (e.g., margin removal), confirm whether users must be able to remove *excess* margin even during losses, and encode that floor explicitly instead of a blanket block.
- If the user wants enforcement only at the API/handler layer, revert core margin changes and move validation there with matching tests.
- When enforcing rules at the handler layer, tests should expect immediate 4xx responses (no reject events) for those cases.
- When suppressing alerting, avoid overly specific string matches; generalize to the error class the user intends (e.g., log-only for "handler not found").
- When the user wants "pull everything" monitoring, avoid relying on `config/feeds.json` allowlists; prefer dynamic venue symbol discovery.
- If the user prefers monitoring from the existing enabled-asset list, use that instead of feed allowlists or dynamic discovery.
- When a tool warning indicates the wrong tool was used, stop and switch to the required tool immediately (e.g., `apply_patch` must be invoked via the tool, not `shell_command`).
- When adding diagnostics on hot paths, avoid per-event heavy work; compute detailed state only on error paths.
- **CRITICAL**: For admin endpoints like `/confiscate-balance`, `raw_amount` is in HUMAN-READABLE format (e.g., `"0.01"` for 0.01 WETH), NOT in wei/smallest unit. The accounts service uses `num.NewTextDecimals(body.GetAmount(), collateral.Decimals())` which treats the input as human-readable. Always verify amount format before providing values to admin endpoints.
- When the user requests avoiding sentinel, refactor tests to use margin services/events directly and remove sentinel dependencies.
- When the user asks to avoid changing test scaffolding (e.g., eventstream/test helpers), keep tests unchanged and fix the implementation instead.
- When a user says a behavioral assertion is intentional ("must change"), do not relax the test; fix implementation semantics and update dependent expectations consistently.
- After fixing a flaky/failing subtest, always run the full owning package to confirm no hidden planner/margin regressions remain.
- When the user asks to run all unit tests directly, run `go test` suites first; do not switch to coverage scripts that can fail for environment/network reasons.
- When creating temporary artifacts for this project, use project-local `tmp/` (e.g., `/Users/yclau/Desktop/aevo/exchange-backend/tmp`) instead of system `/tmp`.
- For margin behavior regressions, check the same test expectations on `master` before changing implementation; if logic is intentionally reverted, align stale test constants to baseline.
- In eventstream-based tests, avoid high-frequency `es.Tick()` goroutines (e.g. 1ms); use bounded low-frequency ticking with timeout to prevent CI watchdog panics.
- For account settings changes (e.g., position mode), mirror validator state checks in handler/read-accessor preflight so obvious invalid requests fail immediately with HTTP 4xx instead of async `COMMAND_REJECT`.
- For hedge-mode features, document both REST and Teller integration paths (including RFQ `create_quote` payloads) in `docs/` immediately after behavior changes.
- When risk policy constants/functions are reused across apps (admin/monitoring), centralize them in a shared `pkg` helper to avoid drift between UI and alerting behavior.
- Avoid placeholder initializations that are always overwritten (e.g., `x := default; x = computed`); initialize directly from computed value to prevent `ineffassign` lint failures.
- Keep Go struct field names consistent with sibling naming patterns (e.g., `*Count` suffix) even when JSON tags are already correct.
- When a newly added E2E test is explicitly rejected by the user as unstable/unwanted, remove the test entirely (not partial assertions) and re-verify the neighboring suite compiles and passes.
- When the user asks for documentation-only output, avoid proposing scripts and deliver a complete docs runbook with exact operational steps and queries.
- For audit exports, if the user asks for all records in a date range, default to full-period queries only and avoid mixing in cutoff/as-of snapshot exports.
- For shell scripts expected to run on macOS, avoid GNU/Bash4-only features (`mapfile`, `sort -V`, non-portable awk captures); use POSIX-compatible patterns.
- For long ClickHouse audit exports, set explicit high client/query timeouts (e.g., `--max_execution_time`, `--receive_timeout`, `--send_timeout`) and keep them configurable via script flags.
- When users ask to remove confusing/non-essential doc content, aggressively prune to the exact operational path they requested (single workflow, minimal branches).
- For large `ReplacingMergeTree` exports under strict server timeout caps, avoid `FINAL` and global `ORDER BY`; use `PREWHERE` and, where possible, key-aligned filters (e.g., `_SeqNo` ranges from `events_history` for `order_history_mm`).
- If optimized single-query exports still exceed server timeout caps, switch to chunked exports (account + time window) and append results into one artifact per requirement.
- When the operator says specific history tables are out of scope for the audit, remove them from both docs and default export flow immediately to reduce runtime/confusion.
- For ClickHouse `TOO_SLOW` estimate-limit failures, increasing timeout is insufficient; reduce query scope/chunk size (e.g., monthly -> daily) for the affected query/table.
- For ClickHouse portability, avoid relying on `WITH` aliases inside `numbers(...)` arguments; use explicit constants/expressions to prevent `UNKNOWN_IDENTIFIER` on some server versions.
- Avoid over-splitting by default; prefer coarse chunks (e.g., monthly) and only increase granularity for specific failing slices.
- Keep split dimensions simple for operators; if requested, prefer time-only chunking over account×time fan-out to reduce perceived runtime/complexity.
- When the user corrects the target instrument/asset mid-debug (e.g., `ME` -> `MOODENG`), immediately pivot all checks and restate conclusions only for the corrected symbol.
- For websocket adapters that build subscriptions from startup state (e.g., funding adapters using enabled assets), ensure runtime config/asset events trigger adapter restart or resubscribe; otherwise admin changes appear to require manual app restart.
- When the user asks for app-scoped behavior (e.g., funding adapter restarts), implement it in that app (`apps/funding`) instead of broad generic adapter logic.
- In `pkg/ts` eventstream tests, do not re-create consumers during `OnEvent` handling; re-creation can leave stale consumer channels and deadlock `SendCommand` ("send command is not progressing"). Prefer in-place adapter restarts.
- For funding logic, when `external_funding_weight == 1` and external rate exists, short-circuit to external funding before internal TWAP computation to avoid `INVALID_FUNDING_TWAP` blocking updates.
- When a user asks to verify PR/review comments, explicitly validate each comment against live code first, then patch only confirmed issues and prove with focused tests.
- When adding fields to `MATCH_ORDER` payloads, update `platform/validator/tag.go` to preserve them when rebuilding `MatchOrderEvent`; otherwise new fields are silently dropped before downstream apps (e.g. history) consume the event.
- When a user reports CI/test panic logs, reproduce the exact failing test first and verify whether failure is code logic vs environment constraints before broad refactors.
- Do not add production struct fields purely for test injection (e.g. adapter factories); prefer mocking at test boundaries or test-only seams so production code stays minimal.
- Never use silent patch-ups anywhere in production code (defaulting/ignoring/masking invalid state). If input/config/state is missing or malformed, return/log explicit typed errors with context so root causes stay debuggable.
- Never "fix" config parsing panics by silently defaulting invalid/missing values (e.g., `external_funding_weight`) to zero; return explicit typed errors and let callers decide handling.
- During PR reviews, explicitly audit changed files for swallowed errors (`_, _`), nil-coercion helpers, and silent early-returns; convert them to explicit logs/errors where appropriate.
- When a user asks for “just a new MCP server,” do not expand scope into adjacent product features (dashboard/visibility/leaderboard) unless explicitly requested; ship the narrow server first.
- When asked to implement a feature, do not rely on historical commit cherry-picks unless explicitly approved; default to a clean from-scratch implementation.
- When the user rejects an incremental approach and asks for "from scratch," immediately re-audit end-to-end behavior (contracts, validator, matching, settlement, API) and re-verify before continuing.
- When explaining margin/risk internals, do not give path-only summaries; include explicit cross vs isolated equations, lifecycle checks, and where each gate is enforced.
- For hedge/liquidation fixes, verify side propagation end-to-end (`liquidator -> engine MATCH_ORDER -> accounts/open-interest`) and lock it with regression tests; mismatched `PositionSide` defaults can silently update the wrong bucket.
- For one-way opposite-direction UX policy, keep enforcement in API/Teller entry handlers; do not place it in shared validator state paths that are also used by internal/eventstream flows.
- When the user asks for a direct "full integration" answer, avoid phased framing; provide one concrete end-to-end structure immediately.
